# Tupã Architecture Overview (Crate-First)

**Last updated:** 2026-05-14

This document describes the architecture of Tupã as a set of Rust crates (crate-first approach). See [PROPOSAL.md](./PROPOSAL.md) for strategic rationale.

---

## Design Principles

1. **Rust-native** — No separate compiler; macros expand to Rust code; `rustc` does type checking.
2. **Zero-cost** — `Safe<T>` and `Tensor` are compile-time proofs with no runtime overhead (erased in release builds).
3. **Deterministic execution** — Channels + sequential steps guarantee reproducible results (given same input & seed).
4. **Extensible** — Plugin system allows runtime addition of custom step functions without recompilation.
5. **SPEC-compliant** — All behavior verified against `docs/reference/spec.md` via conformance suite.

---

## Crate Map

Tupã consiste nos seguintes **crates públicos** (0.9.x):

```text
tupa-core-macros  ← Macro procedural: implementación del pipeline!
tupa-core         ← API pública: tipos (Safe, Tensor), traits
tupa-engine       ← Ejecutor: scheduling paralelo/secuencial, restricciones, métricas
tupa-plugin       ← Sistema de plugins: carga dinámica de funciones externas
tupa-pyffi        ← Bindings Python (PyO3, aún no estable)
cargo-tupa        ← CLI wrapper: cargo tupa <subcomando>
```

**Crates internos/privados:** Ninguno — todos los crates en el workspace son públicos.

**Crates eliminados (pre-0.9.0):** `tupa-parser`, `tupa-lexer`, `tupa-typecheck`, `tupa-codegen`, `tupa-runtime` (antiguo), `tupa-cli`, `tupa-fmt`, `tupa-lint`, `tupa-audit`, `tupa-conformance`, `tupa-effects`, `tupa-sys`, `tupa-lsp`. Estos formaban parte del compilador standalone `.tp` y ya no se mantienen.

## Core Abstractions

### 1. Pipeline Trait

Every pipeline implements:

```rust
pub trait Pipeline {
    type Input: PipelineInput;  // user-defined
    fn name(&self) -> &'static str;
    fn steps(&self) -> &'static [StepDescriptor];
    fn constraints(&self) -> &'static [ConstraintDescriptor];
    fn run_step(&self, ctx: &mut StepContext, step: &str, input: &Self::Input) -> Result<Value, Error>;
}
```text

Generated by `pipeline!` macro.

### 2. Executor

```rust
pub struct Executor {
    scheduler: Scheduler,
    constraint_solver: ConstraintSolver,
    plugin_registry: PluginRegistry,
}
```text

- Creates channels for each step
- Executes steps in order (or parallel if `@parallel`)
- Collects metrics, evaluates constraints
- Returns `PipelineResult`

### 3. Constraint Solver

Two-phase:

- **Compile-time:** constant folding + interval analysis (proves `x == 42`, `x > 0`, `!nan` for literals)
- **Runtime:** evaluates metric expressions against actual values; records pass/fail

Constraint DSL:

```rust
metric("name").operator(value)
```text

Operators: `eq`, `lt`, `le`, `gt`, `ge`.

### 4. Step Context

Each step runs with:

```rust
pub struct StepContext<'a> {
    pub metrics: &'a mut MetricRegistry,
    pub plugins: &'a PluginRegistry,
    pub audit: &'a mut AuditLogger,
}
```text

Steps can read previously computed metrics (by name), call plugin functions, and log audit events.

## Execution Model

1. **Compilation** — `pipeline!` macro expands to impl of `Pipeline` trait. Rust compiler type-checks all step bodies.

2. **Instantiation** — `Pipeline::new()` creates zero-sized struct (no allocation)

3. **Execution** — `Executor::run(pipeline, input)`:
   - Validates input type (requires `serde::Serialize` typically)
   - Creates channel pairs for each step
   - Spawns tasks (one per step) sending `input` through the chain
   - Collects metric values after each step
   - Evaluates constraints against collected metrics
   - Returns `PipelineResult`

4. **Audit** — if enabled, each step's output is hashed (`SHA-256`) and stored in an immutable log.

## Type System Integration

### Compile-Time Checking

Macro expansion takes AST of pipeline DSL, converts to Rust types:

```rust
// DSL
step("x") { input + 1 }

// Expands roughly to
fn step_x(ctx: &mut StepContext, input: &Input) -> Result<Value, Error> {
    Ok(Value::from(input + 1))
}
```text

If `input + 1` is invalid (e.g., `Input` has no `Add` impl), rustc reports error at the step definition site — with full span info.

### Constraint Provenance

`metric("x").eq(5)` where `step("x") { 5 }` is proven at compile time because the value is constant. If step is non-constant, constraint is **runtime-only**.

Proof failures:

```text
error[E3002]: cannot prove constraint at compile time: throughput >= 1000
  --> src/lib.rs:20:5
   |
20 |         metric("throughput").ge(1000.0)
   |         ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
   |
   = hint: The expression for metric "throughput" is not a compile-time constant.
           Move the calculation to a `const fn` or use a literal.
```text

## Data Flow

```text
Input (user)
   ↓
Step 1 (pure fn) → Metric A
   ↓
Step 2 (pure fn) → Metric B [reads Metric A via ctx.metrics.get("A")]
   ↓
...
   ↓
Constraint Checker ← all metrics collected
   ↓
Result { passed: bool, values: HashMap<String, Value> }
```text

All data movement is via immutable borrows (`&input`) or owned values passed through channels. No shared mutable state → no data races.

## Extension Points

### Custom Metric Functions

Define a function returning a value:

```rust
fn compute_sharpe(returns: &[f64]) -> f64 { ... }
pipeline! { ..., step("sharpe") { compute_sharpe(input.returns) } }
```text

### Custom Constraint Operators

Extend via feature flag (unstable):

```rust
tupa_core::constraints::register("volatility", |val, threshold| {
    val < threshold * 0.05
});
```text

### Plugin System

Load shared libraries at runtime:

```rust
use tupa_plugin::PluginManager;

let mut pm = PluginManager::new();
pm.load_plugin("./plugins/strategies.so")?;

// In a pipeline step, call a plugin function:
// let result = pm.call("my_step", json!(input))?;
```text

See `crates/tupa-plugin/` for the plugin API and `create_plugin_template()`.

## Performance Characteristics

| Operation | Cost |
|---|---|
| Pipeline construction (`MyPipeline::new()`) | Zero (ZST) |
| Single step execution | ~ function call + channel send/recv (~100ns) |
| Constraint check | expression eval (~10–100ns per metric) |

- Memory allocation | Only for dynamic types (String, Vec, Tensor heap data) |
- Audit logging | +10–20% overhead (hashing each step output) |

**Benchmarks pending** in Phase 4. Current numbers from ViperTrade integration: ~200ns per step on M2 MacBook.

## Safety Guarantees

- **Memory safety:** Entirely Rust — no segfaults
- **Thread safety:** Ownership-based channels prevent data races
- **Purity:** Optional compile-time check for `#[tupa::pure]` steps (future)
- **Replayability:** Audit log + deterministic steps = reproducible decisions
